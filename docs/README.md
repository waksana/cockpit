## 真相来源与冲突处理

| 问题 | 权威来源 |
| --- | --- |
| 产品应当做什么 | 已确认的 R1–R8；未确认建议不得写成既定要求。 |
| 源码现在做什么 | 当前提交的实现、依赖和已有验证证据；实现文档必须随之修正。 |
| API 接受什么 | [`Intents` / schema](../packages/protocol/src/index.ts)，运行实例的 `GET /capabilities`。文档不另建可执行 API 注册表。 |
| 构建和运行包包含什么 | [`service-delivery.json`](../service-delivery.json)、锁文件及固定产物清单。 |
| 某实例实际运行什么 | 该实例 `/version` 与同实例 `/health`；私有部署还需原 `requestId` 的认证回执。 |
| 模块原件来自哪里 | [`source-inventory.json`](../module-staging/source-inventory.json) 的源 SHA、路径、摘要和 mode。 |

要求与实现不符时，要标明缺口，不能偷偷改要求来匹配代码；实现说明与代码不符时，
修正文档，不把错误说明变成实现授权。历史结论、合成用例、源码推导和线上回读
各有证据边界，不能相互替代。机器可读的 transport 列表包含运维端点，
不表示每条 transport 都是公开产品 intent 或无需认证。

## 维护规则

1. 每次行为变化只在对应主题正文维护细节；其他文档用链接和必要摘要，不复制整段契约。
2. 新建文档先确定它属于哪种性质、替代什么、从哪里进入；没有独立主题就更新现有正文。
3. 当前说明不用“本轮”“稍后”“现在已上线”等无基线说法。部署事实集中记录时间和完整 SHA；
   文档或源码提交不得自动更新成“已部署”。
4. 已退役能力在当前指南只保留明确的不可用和采用说明；旧操作步骤移入历史区，
   不虚构旧名兼容、空成功接口或隐含回退。仍有实现的原生别名按真实契约说明。
5. 归档保留当时结论并标明非当前规范；旧行号和文中路径按原基线理解。
   `module-staging` 的原始副本不为修文档而改字节，亦不整理成可运行模块。
6. 提交前核对相对链接、锚点、命令路径及示例与其真实实现；不为 Markdown 改动启动生产服务
   或重跑无关构建。变更具体声明或记录时保留可追溯来源。

文档维护不会自动产生模块、部署、调度、认证修改或用户数据迁移授权。
